How to read this. You do not put regular expressions inside a .feature file. Those files stay ordinary English. The pattern lives on the Python step that matches the sentence. Your job is to write a clear business line; the pattern is what lets several similar lines share one step.

1. What is a regular expression?

A regular expression (often shortened to regex) is a pattern for text. It does not store one sentence. It describes a shape that many sentences can fit.

Everyday picture: a name badge that says “Hello, my name is ______”. The printed words stay the same. The blank changes. A regex is that badge, written in a compact notation the computer can check.

Literal words

Fixed text that must appear exactly, such as the Mellat cash-out.

A named blank

A slot with a name, such as outcome, filled by the rest of the sentence.

Start and end

^ and $ mean “this is the whole line”, so a longer unrelated sentence cannot sneak in.

In our suite, that looks like this idea: 

the Mellat cash-out  +  <the changing part>

The computer version of the same idea (you will see this on the step, not in Gherkin): 

^the Mellat cash-out (?P<outcome>[A-Za-z0-9 -]+)$

Read it in English: “the line starts with the Mellat cash-out, then a named piece called outcome made of letters, digits, spaces, and hyphens, then the line ends.”

2. Why we use it — and what the point is

Without a pattern, every slightly different sentence needs its own Python step. That clones work, slows reviews, and makes two authors invent two wordings for the same behaviour.

1

Write the family once

One step covers “is credited”, “is rejected”, “is not duplicated” — as long as they share the same opening words.

2

Add a case without a new function

A new similar outcome is a new Gherkin tail plus one dictionary key — not a new @then.

3

Keep Gherkin readable

Product language stays in the feature file. Flexibility stays on the step. Reviewers read English, not a pile of cloned methods.

What you type vs what the framework matches

You write in the .feature file The shared step can match
Then the Mellat cash-out is credited One family: the Mellat cash-out + an outcome
Then the Mellat cash-out is rejected
Then the Mellat cash-out is not duplicated
The point. Regex is not there to make steps look clever. It is there so similar business sentences share one implementation, and so a new sentence in the same family does not require a new Python function.

3. Stem + tail — the picture that makes it easy

Every reusable family has two parts. The stem is unique. The tail is the part that changes.

Stem — stays the same
Pick words no other family uses.
Example: “the Mellat cash-out”
+
Tail — the blank
Ordinary English words.
Example: “is rejected”

Full line the scenario author writes: 

Then the Mellat cash-out is rejected

Do this

  • Search for an existing stem first
  • If the meaning matches, rewrite your English onto that stem
  • If nothing fits, add a family, not a one-off sentence

Avoid this

  • A new step for every unique sentence
  • A long list of full sentences joined with |
  • Putting (a|an) inside the feature file

If the tail is new but the stem is right, the line still matches. The service then lists the known tails. That is helpful: it means you add the new outcome to a dictionary, not a new regex.

4. API example — Mellat cash-out

Same three checks. Left: one Python step per sentence. Right: one family.

Before — three cloned steps
@then("the Mellat cash-out is credited")
def _credited(...): ...

@then("the Mellat cash-out is rejected")
def _rejected(...): ...

@then("the Mellat cash-out is not duplicated")
def _not_dup(...): ...

A fourth outcome means a fourth function, and another review of copy-paste.

After — one family
@then(parsers.re(
  r"^the Mellat cash-out "
  r"(?P<outcome>[A-Za-z0-9 -]+)$"
))
def _mellat_cash_out_then(outcome, ...):
    assert_mellat_cash_out_then(..., outcome)

Gherkin stays three readable lines. Python stays one step plus a dict of outcomes.

What the feature file looks like after

Then the Mellat cash-out is credited
Then the Mellat cash-out is rejected
Then the Mellat cash-out is not duplicated

Incoming draft that does not need a new step — rewrite onto the stem:

Draft wording
Then the Mellat cash-out fails
     because the amount is not allowed
Same meaning, family stem
Then the Mellat cash-out is rejected

5. API example — KYC promissory note

When the set of values is small and will not grow, the blank can be an explicit list of tokens. Still one step — not three.

Before
@then("the promissory note is verified")
@then("the promissory note is unverified")
@then("the promissory note is rejected")

Three names, three functions, one behaviour.

After
^the promissory note is
 (?P<status>verified|unverified|rejected)$

Feature lines stay plain English. The pattern only lists the three statuses.

Growing list of outcomes

Use an open tail and a dictionary — Mellat cash-out style. New outcomes should not force a regex edit.

Frozen 2–4 tokens

Use an explicit list such as jibit|sitaad or verified|unverified|rejected.

Another API family — identity provider

Then the jibit identity inquiry succeeds
Then the sitaad identity inquiry succeeds

Pattern: ^the (?P<provider>jibit|sitaad) identity inquiry succeeds$

6. UI examples — dashboard and visibility

UI steps use the same idea. The changing part is a business object (who, which tile, which element, which state) — never a CSS selector, and never Persian in the feature file.

Opening a feature from the SuperApp hub

Before — one step per feature
When the customer opens landline bill inquiry from the hub
When the customer opens top-up from the hub

Each new SuperApp tile tempted a new function.

After — one hub family
When the customer opens landline bill inquiry from the hub
When the customer opens top-up from the hub

^the customer opens (?P<feature>[A-Za-z0-9 -]+) from the hub$

Add the feature name to the dispatch dict. Do not add a new @when.

Opening a tile from the dashboard

Before — one step per tile
When the staff opens bill inquiry from the dashboard
When the staff opens internet package from the dashboard

Staff dashboard is a different fixture from the customer hub.

After — one dashboard family
When the staff opens bill inquiry from the dashboard
When the staff opens internet package from the dashboard

^the staff opens (?P<tile>[A-Za-z0-9 -]+) from the dashboard$

Do not merge hub and dashboard into one regex with customer|staff. Same English, different fixtures.

Shown or hidden chrome

Before
Then the submit button is shown
Then the submit button is hidden
Then the amount field is disabled
After
^the (?P<element>[A-Za-z0-9 ]+) is
 (?P<state>shown|hidden|enabled|disabled)$

Where Farsi lives

English in the scenario. Persian copy in tests/ui/labels/. The page object maps bill inquiry to the label on screen. Regex never captures a CSS path.

7. A short map of symbols you will see

You do not need every regex feature in the world. These are the ones this project actually uses on steps.

You seeIt meansFriendly reading
^ ... $ Start and end of the whole line Match this sentence, not a longer one that contains it
(?P<name>...) A named blank Call this piece outcome or tile and pass it to Python
[A-Za-z0-9 -]+ One or more allowed characters Letters, digits, spaces, hyphens — ordinary English words
verified|unverified This word or that word A short closed menu, not a growing story
(?:the )? Optional extra words Only when existing scenarios already mix “the” and no “the”
routes? Optional “s” route or routes — only when current files already mix both
Melli(?!t) Look ahead and refuse a follow-on letter Match Melli without stealing Mellat
Numbers and quoted values. Amounts, tracking codes, and exact expected strings belong in an Examples table or in quotes in the sentence — not stuffed into the open word tail.

8. How we made this easy to use — the Cursor skill

The rules are already in the repo. The skill packages the workflow so you do not have to remember every regex detail while you write a scenario.

The skill file

.cursor/skills/bdd-step-regex/SKILL.md

Search existing families. Rewrite Gherkin onto a stem. Extend a family instead of cloning a step.

Worked examples

.cursor/skills/bdd-step-regex/examples.md

API and UI patterns, plus real collision traps (Melli vs Mellat, Manual vs Nemo wording).

Auto-attached

When you edit a .feature file, a step file, or a *gherkin.py file, Cursor loads this workflow.

What the skill does for you

  • Looks up existing stems before adding a new @given / @when / @then
  • Rewrites your draft English onto a family when the meaning already exists
  • If a new family is required, uses a unique stem and an open tail — not a list of full sentences
  • Keeps Zephyr cases as separate Scenario rows; reuse happens through shared steps, not by collapsing tickets into one Outline

Three ways to invoke it

HowWhen it helps
Type @ and attach bdd-step-regex or the SKILL.md file You want to be sure the agent reads the workflow
Say “follow the bdd-step-regex skill” in Agent mode You are already in a chat about a scenario
Just edit a feature file and paste one of the prompts on the next pages The glob rule already puts the skill in context; the prompt tells it what to do

Use Agent mode when you want files changed. Use a review-style prompt when you only want a report first.

A 30-second habit

  1. Write the business sentence you would read in Zephyr.
  2. Paste a prompt from this page and attach the skill.
  3. Prefer “rewrite onto a stem” over “add a new step”.
  4. Skim the before/after the agent prints, then push.
